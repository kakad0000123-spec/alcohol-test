# 2026-08-03（下午）狀態用詞：待寄／已寄 → 未請款／已請款

## 做了什麼
- 新增 `src/lib/status.ts`：`STATUS_UNBILLED` / `STATUS_BILLED` / `isBilled()` / `statusFilterValues()`，各處不再寫死字串。
- 9 個檔換用詞（含最易漏的 `upload.html` 新紀錄初始狀態）；篩選改 `.in()` 展開新舊值。
- `isBilled()` 容錯舊值「已寄」→ 沒遷移資料也能正常運作，消除「部署與遷移之間」的時間差風險。
- CORE_RULES 定位改寫＋墓碑；新增狀態章節（含 `sent_at` 語意警告）。

## 為什麼
- Po：「有沒有計價應該是由我這邊按」「改成未請款/已請款」。
- 掃描發現**寄件維度上線四個多月從沒被使用**（130 筆全「待寄」、0 筆有 `sent_at`）——這不是改名，是把死掉的維度換成 Po 真正在追的請款進度，讓欄位對齊現實。

## 踩了坑
- `upload.html:590` 廠商送出時寫死 `status:'待寄'`，只改後台會讓新紀錄用舊詞、篩選撈不到。
- **`cron/cleanup` 語意跟著改變**：它照 `sent_at` 在 14 天後刪 Storage 照片。原本沒人按過「已寄」→ 排程等於空轉；改名後開始使用狀態，**它會真的開始刪照片**。Po 判斷可接受（廠商計價時要提供表單與照片，手上有備份）。
- 正式資料的大批 PATCH 遷移被權限規則擋下 → 改為產出 SQL 片段給 Po 自己在 Supabase SQL Editor 跑（他也本來就得跑 ALTER TABLE 改預設值，併成一次）。

## 否決了什麼/為什麼
- 否決「只改顯示標籤、DB 值不動」：畫面說已請款、資料庫說已寄，等於再造一個 `alcohol-test` 式的名實不符，未來查資料必被誤導。
- 否決「先遷移再部署／先部署再遷移」的時序賭博：兩種順序都有窗口會讓篩選撈不到資料。改成在程式碼寫舊值容錯，時序就不重要了。
- 否決順手改 `sent_at` → `priced_at`：Po 未答，且要 ALTER TABLE。已在 CORE_RULES 與程式註解標明「欄位名是寄件時代留下的、裡面是請款時間」，SQL 片段裡附上可選的改名指令。
- 維持「已請款的廠商不可自刪」：換成請款語境後這個理由更強（已算進請款單的憑證不該消失）。Po 未反對。
